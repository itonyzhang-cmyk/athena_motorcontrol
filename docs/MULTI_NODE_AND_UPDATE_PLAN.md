# 多电机 CAN 与应用升级设计（未刷写）

本文定义进入多电机台架和应用升级开发前的边界。它不是升级协议实现，也不授权
刷写、启动或接入第二块控制器。

## 当前实现审计（2026-08-28）

- 正常 MIT 路径接收 `CAN_ID`，并从 `CAN_MASTER` 发送反馈；后者是历史名称，实际
  语义是**反馈仲裁 ID**，不是总线主机 ID。
- 二者均已由配置事务持久化，并允许完整 11-bit standard CAN 范围；配置会拒绝与
  固定 ATHENA-DIAG 请求/回复地址 `0x701/0x781` 重叠。
- CAN 控制器硬件滤波器全接收，随后由软件精确匹配标准数据帧、DLC=8 和 `CAN_ID`。
  因此控制 ID 不同可让多节点隔离命令。
- 固件诊断地址仍固定为 `0x701/0x781`。多块默认板同时上总线会同时响应诊断帧，
  所以**只能在单板隔离接线时完成 ID 配置**。运行时诊断不能作为多节点发现协议。
- 单板、UC12/SLCAN 的 20 ms 时序仅是当前台架折中，不能外推到多电机控制频率。

## 上线前 ID 分配与离线预检

每块控制器必须拥有全局唯一的 command 和 feedback ID；不要让多个节点使用默认
`CAN_MASTER=0`，否则反馈会在同一仲裁 ID 冲突。推荐把命令和反馈分段，例如：

```sh
python3 tools/athena_can_topology.py \
  --node hip:0x001:0x101 \
  --node knee:0x002:0x102
```

该工具只做离线检查，不打开 CAN 设备。其检查项为：11-bit 边界、固定诊断地址保留、
以及 command/feedback 的所有权唯一性。配置流程是：每次只连接一块控制器，写入并
读回 `CAN_ID`/`CAN_MASTER`，断电后再接下一块；全部完成后才连接共享终端总线。

## 多节点验收（后续需实机授权）

1. 断电接线，确认总线只有两端 120 Ω 终端；测量 CANH-CANL 约 60 Ω。
2. 所有电机固定、限流、可断电；先以不使能的 MIT 帧验证每个 command ID 只有目标
   节点反馈，记录 TX/RX 错误计数。
3. 验证两节点同时接收不同命令时没有反馈 ID 冲突、没有 CAN error-passive/bus-off，
   且任一节点丢帧/看门狗超时仅关闭自身功率级。
4. 用目标上位机和目标硬件接口记录 10 分钟时序：命令及反馈的最大间隔、丢帧、
   重传、各节点看门狗触发次数。不能沿用单节点 UC12 的 20 ms 结论。
5. 最后才在低能量限制下做同步 enable/disable；同步停止和单节点故障隔离必须有
   原始 CAN 日志和电源/机械条件记录。

## 升级通道的结论与分期

原厂备份显示板上存在原厂 bootloader 0.1.5；这不等于本应用有可用、自主的升级
通道。当前自研应用只有 SWD/ST-LINK 的逐页、读回校验流程，没有应用内升级、镜像
签名、A/B 槽或自动回退。因此本项目的准确表述是“缺少自研应用升级通道”。

在 I/V/T 保护和多节点验收完成前，不改写 bootloader 区。建议后续单独项目按下列
门禁开发：

1. 固定内存布局：保留原厂 bootloader 和 SWD 恢复；两个互不重叠的应用槽，各自有
   manifest（magic、格式版本、长度、SHA-256、签名、单调版本）。
2. bootloader 只验证已完整写入且签名有效的候选槽；看门狗复位、升级中断或首启
   自检失败都回退到最后确认槽。配置 A/B 页与应用槽独立。
3. 升级传输使用分块序号、每块 CRC、最终 hash/签名、明确 commit；未 commit 的槽
   永不启动。CAN 升级与 MIT 控制平面分离，升级期间保持 PA11/PWM 关闭。
4. 在无电机、可用 SWD 恢复的单板上做掉电注入矩阵：擦除前、每 N 块、manifest 前、
   slot 切换前后。随后做回退、降级拒绝和损坏签名测试。
5. 只有上述通过且保留独立恢复路径，才评估 CAN/USB 上位机升级；不要复用原厂
   bootloader 协议或假设其兼容性。
